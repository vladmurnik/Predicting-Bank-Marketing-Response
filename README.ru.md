# Bank Marketing: скажет ли клиент «да»?

[English](README.md) · **Русский**

Это бинарный классификатор на датасете UCI Bank Marketing. На входе — клиент
и контекст кампании, на выходе — согласится ли он на срочный депозит.

---

## Цифры

Тестовое окно: май–ноябрь 2010, последние 20% файла. Я посмотрел на него один
раз, когда все решения уже были зафиксированы.

| Метрика | Значение |
| --- | --- |
| PR-AUC | **0.527** (prior 0.308, ×1.71) |
| ROC-AUC | **0.748** |
| Brier | **0.191** |
| Precision при бюджете 30% | **0.551** |
| Recall при бюджете 30% | 0.536 |

| Precision случайного отбора 30% | 0.308 |

Это впечатляющие цифры? Не рядом с ноутбуками, где есть `duration`. Но те
ноутбуки жульничают, и сейчас я покажу, как именно.

## Как это работает

### 1. Время идёт в одну сторону

Строки в файле хронологические, поэтому сплит по времени: первые 80% — train,
последние 20% — test. Без перемешивания и без «только один разочек».

Для сравнения я прогнал и случайный сплит. PR-AUC подскочил с 0.086 до 0.206.
Это не лучшая модель — это модель, которая подсмотрела будущие месяцы. Оставил
цифру в отчёте как напоминание себе.

### 2. Ловушка утечки

`duration` — длительность последнего звонка. Это ещё и самый сильный признак
в датасете. С ним CV PR-AUC вырастает с 0.086 до 0.402 у логистической
регрессии и с 0.076 до 0.456 у HistGradientBoosting.

Одна маленькая проблема: ты не знаешь, сколько длился звонок, до того как
решил позвонить.

Поэтому я выкинул признак и написал `tests/test_leakage_guard.py`, который
падает, если кто-то — включая меня будущего — вернёт его обратно.

### 3. Четыре модели, одно правило

Сравнивал `DummyClassifier` (всегда prior), логистическую регрессию,
HistGradientBoosting и LightGBM на одинаковых фолдах. Правило выбора
зафиксировал до того, как трогать holdout: максимальный ROC-AUC на последних
20% обучающего окна.

Победила логистическая регрессия (0.575 против 0.544 и 0.560). Разница в
пределах шума — и это отдельный урок: на этих данных большая модель не даёт
устойчивого преимущества, а линейная лучше переносит сдвиг распределения.

### 4. Проблема порога

Оптимальный по F1 порог на validation был 0.03. На test порог 0.03 позвал
99.2% базы. Ничего не сломалось — просто доля согласий выросла с 12.7% до
30.8%, и то же число в новом режиме значит совсем другое.

Поэтому я перестал делать вид, что вероятности переносятся. Рабочая точка —
бюджет: звоним верхним 30% по score, а порог пересчитываем как 70-й процентиль
каждой партии. На test это даёт precision 0.551 против 0.308 у случайных 30%:
столько же звонков, почти вдвое больше попаданий.

### 5. Где ломается

В отчёте есть калибровка, permutation importance, срезы по месяцам, профессиям,
возрасту и числу `unknown`, плюс худшие false positives и false negatives.
Короткая версия: в режиме 2010 модель полезна, в 2008–2009 — заметно слабее.
Время делает большую часть работы, и я говорю это вслух, а не прячу.

## Запуск

```bash
uv sync
uv run python -m bank_marketing.cli all
```

На Windows без GNU make:

```powershell
uv run python make.py repro
```

Скрипт скачивает датасет (~1 МБ, zip внутри zip — да, серьёзно), обучает модели
и пишет `reports/report.md`, `reports/metrics.json` и `models/model.joblib`.

## API

```bash
uv run uvicorn bank_marketing.serve:app --host 127.0.0.1 --port 8000
```

**Живое демо:** пока не задеплоено. Добавлю ссылку сюда, когда подниму.

Сервис принимает одну сырую строку клиента и возвращает `probability`,
`threshold`, `prediction` и `model_version`. `duration` отбивается схемой
запроса, так что утечка не пролезет и через API.

## Чему научился

* Случайный сплит может заставить почувствовать себя гением. Он врёт.
* Самый сильный признак часто оказывается тем, которого не будет в проде.
* Порог — это не бизнес-решение. Бизнес-решение — это бюджет.
* Если у двух окон разная доля положительного класса, сравнивай precision при
  одинаковом объёме, а не F1 при разном.
* Тест, который блокирует утечку, оказался полезнее ещё +0.01 PR-AUC.
