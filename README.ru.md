# Предсказание отклика на банковский маркетинг

Бинарная классификация на [датасете UCI Bank Marketing](https://archive.ics.uci.edu/dataset/222/bank+marketing): по профилю клиента и контексту кампании предсказать, согласится ли он на срочный депозит.

Пайплайн использует хронологический сплит, исключает признак `duration` (он неизвестен до звонка), сравнивает четыре модели на одинаковых фолдах, выбирает рабочую точку по бюджету звонков, а не по фиксированному порогу вероятности, и отдаёт модель через FastAPI.

## Результаты

Тестовое окно: май–ноябрь 2010, последние 20% файла. Оценка выполнена один раз, после фиксации выбора модели и логики порога.

| Метрика | Значение |
| --- | --- |
| PR-AUC | **0.527** (prior 0.308, ×1.71) |
| ROC-AUC | **0.748** |
| Brier score | **0.191** |
| Precision при бюджете 30% | **0.551** |
| Recall при бюджете 30% | 0.536 |
| F1 при бюджете 30% | 0.543 |
| Precision случайного отбора 30% | 0.308 |
| F1 «звонить всем» | 0.471 |

PR-AUC ниже, чем в результатах с `duration`. Этот признак недоступен в момент скоринга и исключён.

## Пайплайн

### Сплит по времени

Строки в файле хронологические, поэтому сплит по времени: первые 80% — train, последние 20% — test. Без перемешивания.

Для сравнения измерен и случайный сплит: PR-AUC вырос с 0.086 до 0.206. Разница возникает из-за утечки будущих месяцев в train, а не из-за лучшей модели. Число оставлено в отчёте как ориентир.

### Защита от утечки

`duration` — длительность последнего звонка и самый сильный признак в датасете. С ним CV PR-AUC вырастает с 0.086 до 0.402 у логистической регрессии и с 0.076 до 0.456 у HistGradientBoosting.

Признак исключён, потому что длительность звонка неизвестна до самого звонка. `tests/test_leakage_guard.py` падает, если `duration` вернут в контракт признаков или в схему API.

### Модели и выбор

Четыре кандидата сравниваются на одинаковых фолдах: `DummyClassifier` (всегда prior), логистическая регрессия, HistGradientBoosting и LightGBM. Правило выбора зафиксировано до обращения к holdout: максимальный ROC-AUC на последних 20% обучающего окна.

Выбрана логистическая регрессия (0.575 против 0.544 и 0.560). Разница в пределах шума: на этих данных большие модели не дают устойчивого преимущества, а линейная лучше переносит сдвиг распределения.

### Рабочая точка

Оптимальный по F1 порог на validation был 0.03. На тестовом окне он позвал бы 99.2% базы: доля положительных выросла с 12.7% до 30.8%, поэтому один и тот же порог вероятности выбирает разный объём.

Поэтому рабочая точка задаётся бюджетом: звонить верхним 30% по score и пересчитывать порог как 70-й процентиль каждой партии. На holdout это даёт precision 0.551 против 0.308 у случайных 30% при том же числе звонков.

### Анализ ошибок

В `reports/report.md` есть кривые калибровки, permutation importance, срезы по месяцам, профессиям, возрасту и числу `unknown`, а также false positives и false negatives с наибольшей уверенностью. В режиме 2010 модель работает лучше, в 2008–2009 — заметно слабее; в отчёте это указано явно.

## Запуск

```bash
uv sync
uv run python -m bank_marketing.cli all
```

На Windows без GNU make:

```powershell
uv run python make.py repro
```

Команда скачивает датасет (~1 МБ, zip внутри zip), обучает модели и пишет `reports/report.md`, `reports/metrics.json` и `models/model.joblib`.

Запуск тестов:

```bash
uv run pytest
```

Тестам не нужен датасет. Два последовательных запуска `cli all` дают идентичный `reports/metrics.json` (seed 42).

## API

```bash
uv run uvicorn bank_marketing.serve:app --host 127.0.0.1 --port 8000
```

**Живое демо:** пока не задеплоено.

Сервис принимает одну сырую строку клиента и возвращает `probability`, `threshold`, `prediction` и `model_version`. `duration` отбивается схемой запроса.
